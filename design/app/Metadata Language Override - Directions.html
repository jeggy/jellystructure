Choosing the metadata language, per title

The resolver walks a file's audio tracks in physical order and fetches TMDB in the first language that answers. For 열배 that lands on kor — correct about the film, wrong about what you want to read. This adds one manual escape hatch: choose a different winner for this one item. Automatic resolution stays the default and stays untouched, and English is only the example — any language TMDB holds is selectable, in either direction.

The page currently conflates three different languages

Original language

TMDB's own original_language — ko. A fact about the film. Never editable.

Resolved language

The winner of the audio cascade — kor, from 0:a:0. Describes the file.

Metadata language

What we fetch title, overview and artwork in. Today it silently equals the resolved language. This is the one you get to choose.

Every direction below keeps the trace visible after a choice. You should always be able to see what the resolver would have done — a choice that hides its own cause becomes a mystery six months later.

Held constant from your answers

  • Per title only. No rules, no per-library default, no global preference. One item at a time, for the rare edge case.
  • One language for text and artwork together. Poster/backdrop candidates follow the same pick.
  • Gaps behave exactly as they do today. Choosing a language is choosing a different winner — the existing fetch logic and its existing fallback handle the rest. Nothing new is flagged.
  • The list shows only what TMDB actually holds for this title, each row carrying how complete it is.
  • 열배 lives in the admin only. Ravilo shows exactly the language you chose.
  • A series is chosen as a whole. Per-episode resolution keeps running underneath; the choice sits above it.
  • English is an example, not a destination — any language TMDB has is selectable, including going the other way.

Direction A, and what still needs deciding

A, with the per-language coverage read-out from B folded into its picker. The control sits where the question gets asked, the trace stays visible underneath, and choosing a language does one thing: it names a different winner. Everything after that — fetching, filling fields, picking artwork, writing the NFO — runs the code that already exists, with no new warning states, no new flags, and no new empty-field handling. If TMDB lacks a field in the chosen language, whatever happens today for an automatically-resolved language happens here too.

The invariant I'd write into the spec: choosing a language changes which language we ask TMDB for, and nothing else. It never edits a track, never changes a default flag, never touches the file, and never alters the resolver — the cascade keeps running underneath and stays visible. The constitution's "language resolution is per-file, first TMDB hit wins" stays true; the choice is a layer above it, not an edit to it.

Behaviour worth pinning before anyone builds

  • The choice is a lock. Same shape as Phase 151/174: pull_tmdb, a re-scan and a Jellyfin re-pull all keep it. Otherwise the next scan silently undoes your work.
  • Downstream is unchanged. No field gains a warning, nothing new enters Triage, and the Metadata tab can't tell a chosen winner from a resolved one.
  • TMDB gains translations over time. A later pull picks them up on its own — the choice re-fetches like any other item rather than freezing a payload.
  • Series: one choice for the whole show. Per-episode resolution still runs (episodes have their own tracks), but every episode fetches in the chosen language. An episode whose own audio differs does not escape it.
  • Ravilo is unaffected as a system — it receives whatever the admin stored. No client work, no new strings.

Open questions for the dev review

  • Is GET /movie/{id}/translations cheap enough to call when the picker opens, or does the coverage read-out need caching on the item? A series needs the same call per season for episode coverage.
  • Does the artwork side use include_image_language=<chosen>,null, or does the choice steer text only? Your answer said text and artwork together — this is where "together" gets specific.
  • What does the NFO carry — a field recording the chosen language so Jellyfin and a future re-import agree, or is it invisible outside our DB?
  • Does the Library workbench need a Metadata language facet, or is the chip enough to find these again?
