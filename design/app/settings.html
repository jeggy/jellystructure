What Jellyfin is set to today, where that costs this hardware something, and exactly where to change it. A setting that already matches the recommendation shows nothing at all — no row, no green tick. On this server the transcode path is already a RAM disk and /config+/cache are already on NVMe, so neither is mentioned below. Nothing here is a defect; every one is a trade-off, and each row says what turning it off costs you.

JellyfinThrottle Transcodesoff
A client that pauses or seeks leaves its ffmpeg writing segments at full speed instead of easing off — reads this disk can't spare during playback. Time to throttle after is already set to 180 s and has never once applied: it is inert until throttling itself is on, which is exactly what makes this hard to notice.
Dashboard → Playback → Transcoding → turn Throttle Transcodes on
Trade-off: a throttled transcode has less buffer built up, so a big seek can take a moment longer to recover.
JellyfinDelete segmentsoff · keep 720s
Finished segments are never removed during a session, so a long film accumulates the whole way through. This one only matters because the transcode path is already a RAM disk — segments pile up in memory rather than on a disk with room to spare. jellystructure can't see Jellyfin's own mounts from inside its container, so the RAM part is inference; the setting itself is read straight from Jellyfin.
Dashboard → Playback → Transcoding → turn Delete segments on, keep Time to keep segments at 720 s
Trade-off: a viewer who rewinds past the keep window makes Jellyfin transcode that stretch again.
JellyfinAllow encoding in HEVC formatoff
Hardware encoding is on, but HEVC output is disallowed, so every transcode lands as H.264 — more bitrate for the same picture, over the same link. BRAVIA 4K GB ATV3 and 2 other devices have a recorded HEVC decode ceiling, which is how we know they'd take it.
Dashboard → Playback → Transcoding → consider turning Allow encoding in HEVC format on
Trade-off: an older client that asks for a transcode may not decode HEVC at all. Worth testing per device rather than assuming.
JellyfinOn-demand metadata-based keyframe extractionmkv, mp4
A seek in a file without a usable index can make Jellyfin scan the whole file for keyframes — a full linear read of a remux, on a rotational library, triggered by someone dragging a scrub bar. There is no switch for this in Jellyfin's UI: it lives only in encoding.xml, as AllowOnDemandMetadataBasedKeyframeExtractionForExtensions.
Edit encoding.xml and empty that list. No admin-panel equivalent exists — we're not sending you to hunt for a toggle that isn't there.
Trade-off: seeking in files with no index gets less accurate.

HostI/O scheduler on sdcmq-deadline
Background ffmpeg here already runs under nice -n 19 ionice -c3 — jellystructure has done that since Phase 109, to protect playback. mq-deadline ignores ionice completely, so that protection has never taken effect once. Switching to BFQ makes an already-written mitigation start working, and gives the film being watched latency priority over batch readers — exactly the contention that stalled The Patriarch.
Switch to BFQ (the module is present on this kernel):
echo bfq > /sys/block/sdc/queue/scheduler
Trade-off: BFQ costs a little more CPU per request and can shave peak sequential throughput. This box sat at 0.15 % CPU pressure while the disk was saturated, so it's the right trade here — but it is a trade. Does not survive a reboot — needs a udev rule to persist.
HostRead-ahead on sdc128 KB
Every read of a 4K remux is broken into small requests, each paying a seek. Raising it means fewer, larger sequential reads. A minor lever, listed second on purpose: a 24.7 GB film was 0.7 % resident in a 102 GB page cache, so the big win on this host isn't read-ahead at all.
Raise to 8–16 MB:
echo 16384 > /sys/block/sdc/queue/read_ahead_kb
Trade-off: more memory held per reader, and wasted reads if access turns out random. Does not survive a reboot.
HostMax request size on sdc1280 KB of 32767 KB
The hardware will take requests 25× larger than the queue currently allows, so a 16 MB read-ahead gets split into ~13 requests anyway — the row above is partly wasted without this one.
Raise toward the hardware ceiling:
echo 32767 > /sys/block/sdc/queue/max_sectors_kb
Trade-off: a single huge request can hold the queue longer, which matters more without BFQ than with it. Does not survive a reboot.
JellyfinEnable chapter image extractionon
Generates a still per chapter for every title in this library — each one a full linear read of a remux off a rotational disk. Extract chapter images during the library scan is on too, which moves that work into every scan instead of leaving it to the nightly task. Jellyfin's own help text makes the argument: “The process can be slow, resource intensive, and may require several gigabytes of space… It is not recommended to run this task during peak usage hours.”
Dashboard → Libraries → Movies → Manage library → turn Extract chapter images during the library scan off; turn Enable chapter image extraction off too, or keep it knowing the cost
You lose: the chapter-image menu when picking a scene. Chapter markers stay.
JellyfinExtract trickplay images during the library scanon, but inert
A contradictory pair: Enable trickplay image extraction is off for this library, so the during-scan flag does nothing at all. Nothing is being wasted — but one of the two doesn't mean what it says, and that's a mistake at any disk speed.
Dashboard → Libraries → Movies → Manage library → pick one: turn the during-scan flag off, or turn the feature on if scrub previews were the intent

    Seeding snapshot freshness

    Phase 99
    The seeding & cross-seed views (and the library seeded-on filter) read one shared, cached snapshot of qBittorrent rather than querying per title. This is how often that snapshot is auto-refreshed — a longer interval is lighter on qBittorrent; Refresh now on any seeding view always forces an immediate re-query.
    minutes
    Default 10 minutes. Range 1–60 min. Set lower if you cross-seed frequently and want the view fresher; higher to minimise load.
    Fail-closed: if the guard is enabled but qBittorrent is unreachable, edits are blocked (rather than risking a seeded file) until it responds or you disable the guard.

    Memory budget suggest-only host 125 GB · 23 GB used · 102 GB page cache · swap 47 GB (12 GB in use)
    This host's memory is enormous and entirely ungoverned — Jellyfin runs with no memory limit at all, and its /transcode is a 63 GB RAM disk that nothing bounds. Nothing has fallen over; nothing has been decided either. Say how much of the machine the media stack may use and this works out what to change.
    GB of 125 16326496
    ~/jellyfin/docker-compose.yml
    Jellyfin has no limit today. Adding one trades “the host OOMs unpredictably” for “Jellyfin gets OOM-killed predictably” — mid-film that is better, but it isn't good. It's also the only thing that makes every other number here real: jellyfin, immich_server, immich_postgres and umami-db all run unbounded, and OOM scores are effectively tied (671 vs 678), so today the kernel picks its victim by size — the process serving a film is as likely as a batch job.
    ~/jellystructure/docker-compose.yml
    Already bounded at 16g, and it measures ~3.0 GB in practice — it was never the unbounded one. Left as is.
    HostCap the transcode RAM disk63 GB, uncapped
    /transcode is a bind mount of the host's /dev/shm, so the container's own shm_size: 64 MB does not bound it — it defaults to half of RAM. tmpfs pages are not reclaimable: the kernel can't drop them under pressure, only swap them and then start killing. That makes this the one real break path in the whole budget.
    Give the mount an explicit size, and turn segment deletion on — these are one change, not two:
    Dashboard → Playback → Transcoding → turn Delete segments on, leave Time to keep segments at 720 s. Jellyfin currently reports it off, so a long 4K transcode accumulates segments in RAM for the whole session.
    Also worth capping: /tmp is a second 63 GB RAM disk already holding 6.2 GB. Not ours, same hazard — a budget that caps one and ignores the other has bounded half the problem.
    Hostvm.swappiness60
    The kernel is paging out live processes to grow a cache it doesn't need — 12 GB swapped out against 102 GB cached. Wrong trade when one of those processes is serving video.
    sysctl -w vm.swappiness=10 # persist: echo 'vm.swappiness=10' > /etc/sysctl.d/99-swappiness.conf
    This is the one line here that disappears on its own once it's right — swappiness is host-wide and genuinely readable, unlike Jellyfin's compose file or the host's tmpfs size, which this container simply cannot see.
    If another service later takes 60 GB: page cache is reclaimable, so anything cache-shaped just gets evicted and playback falls back to disk — it degrades on its own, correctly. tmpfs can't be dropped at all, which is why the cap above matters more than any other line. Today's real usage is small — Jellyfin 3.5 GB, jellystructure 3.0 GB, nothing else above 1.3 GB — so a 60 GB neighbour would fit right now without touching a thing. The risk isn't the neighbour; it's the neighbour arriving while an uncapped transcode is filling RAM.
