requirements & delivery plan · v0.1 · draft

Jellystructure

A self-hosted, Docker-deployed web system that fully replaces Jellyfin's built-in metadata scraper — owning NFO files, artwork, and the media containers themselves (audio/subtitle track order), driven by a language-cascade rule and updated live in the browser.

Backend: Kotlin Native · Ktor CIO Frontend: Kotlin WASM · real DOM Deploy: Docker Compose Config: TOML

1 · Vision & principles

Jellystructure is the single source of truth for media metadata. Once it manages a library, the operator should never run Jellyfin's "Refresh Metadata" again — Jellystructure writes locked NFO files and artwork to disk and tells Jellyfin only to reload them.

  • Own the file, not just the database. It edits NFO, images, and the MKV/MP4 containers (default audio/subtitle track, order, removal).
  • One rule drives everything. A language cascade decides both the metadata-fetch language and the default track per file.
  • Nothing silent. Long operations stream live progress; the operator always sees what tool ran and what it did.
  • Power-user first, single operator. Dense, keyboard-friendly, self-hosted; not a multi-tenant product.
  • Lightweight. No JVM; small memory footprint and fast cold start suited to a home server container.

2 · Functional requirements

2.1 Configuration MUST

IDRequirementAcceptance
FR-C1Store all settings in a human-readable config.toml on a persistent volume.Settings survive container restart; file is valid TOML.
FR-C2Edit config from the website — both a sectioned form and a raw TOML view of the same data.A change in either view persists to disk and is reflected in the other.
FR-C3Manage: TMDB v3 API key; Jellyfin base URL + API token; library path mappings (see FR-C5–6); behaviour toggles; global fallback language (single language, default en).Each setting round-trips form → TOML → form.
FR-C4"Test connections" verifies TMDB and Jellyfin credentials and shows the literal result/status.Bad key shows a clear failure; good key shows success.
FR-C5Discover available libraries from the connected Jellyfin instance (GET /Library/VirtualFolders) and display each library's name and collection type in the UI. Discovery is triggered automatically after a successful connection test.After a successful connection test the library list updates without a page reload; the list reflects the current state of the Jellyfin server.
FR-C6For each discovered Jellyfin library the operator may either assign a local filesystem path (the folder Jellystructure can read/write) or mark the library as skip. Skipped libraries are entirely ignored during scans. The mapping is persisted as a [[libraries]] TOML array (fields: jellyfin_id, name, collection_type, local_path, skip).Only non-skipped libraries with a valid local_path are scanned. Changing a mapping and saving updates the TOML without touching unrelated config sections.

2.4 Media container manipulation MUST

IDRequirementAcceptance
FR-T1Read every embedded audio/subtitle track via ffprobe: index, codec, language tag, default/forced flags, title.Track list matches the file's real streams.
FR-T2Set the default track / reorder via mkvpropedit (header-only, no re-encode) for MKV. Manual only — initiated explicitly by the operator from the UI; never applied automatically.Default flag changes in < ~100ms with no bitstream rewrite.

FR-T5Show the exact command that will run before applying; support a dry-run plan across many files.Dry run lists affected files + chosen tool with nothing written.

2.5 Language resolution for TMDB metadata MUST — the core feature

The system determines the TMDB fetch language per file based on the file's actual audio tracks. Track ordering and default flags are never changed automatically; they are always a manual operator action (see §2.4).

IDRequirementAcceptance
FR-L1Configure a single global fallback_language (default en) used when TMDB has no entry in any of the file's track languages.Setting saved to [language_rules] fallback_language; only one language allowed.
FR-L2Resolve the TMDB fetch language per file: query TMDB for each language found in the file's audio tracks, in physical track-index order (track 0 first, track 1 next, etc.); use the first language that returns a result. If no track language yields a result, use fallback_language.File with tracks [fo, da]: tries TMDB in Faroese → if no result, tries Danish → if no result, uses fallback. File with tracks [da, fo]: tries Danish first.
FR-L3The resolved language governs the metadata-fetch language only (title, plot, genres, etc. fetched from TMDB in that language). It does not automatically change any track default flag or ordering.Metadata is written in the resolved language; no file track is touched by language resolution.
FR-L4Support a per-library / per-folder override of fallback_language on top of the global default.Most-specific path wins; others fall back to global.
FR-L5Provide a live resolver preview: enter a file's track languages → see which TMDB language would be fetched and what metadata fields would be written.Preview output matches the engine's real decision; runs in WASM with no round-trip.

2.8 Real-time UI MUST

IDRequirementAcceptance
FR-U1Stream job progress to the browser over WebSocket — filenames, ffmpeg %, NFO/artwork status, errors — no polling. 2.9 Authentication — sign in with Jellyfin MUST

Auth works exactly like Jellyseerr/Overseerr: there is no separate Jellystructure account. The operator signs in with their existing Jellyfin username + password; Jellystructure authenticates those credentials against the Jellyfin server and creates its own session. Only Jellyfin administrators may use Jellystructure.

IDRequirementAcceptance
FR-AUTH1Login screen takes a Jellyfin username + password and authenticates via POST /Users/AuthenticateByName against the configured Jellyfin server. Jellystructure never stores the password.Valid Jellyfin creds log in; the password is never written to disk or DB.
FR-AUTH2Only users whose Jellyfin Policy.IsAdministrator is true are admitted; everyone else is rejected with a clear message.A non-admin Jellyfin user cannot get a session.
FR-AUTH3On success, mint an opaque server-side session token (stored in the local DB), set it as an HttpOnly, SameSite=Lax cookie, and gate every API + WebSocket route behind it.Unauthenticated requests get 401; the WebSocket upgrade is rejected without a valid session.
FR-AUTH4Sessions are revocable and expire; logout deletes the server-side token. Session lifetime is configurable.After logout or expiry the cookie no longer grants access.
FR-AUTH5The per-user Jellyfin access token returned at login is distinct from the machine jellyfin_token in settings used by background jobs (FR-J1). Background refreshes must work with no user logged in.A scheduled/auto job triggers a Jellyfin refresh while no browser session exists.

3 · Architecture & non-functional requirements

IDRequirement
NFR-1Backend in Kotlin Native (no JVM) — small footprint, fast cold start; talks to POSIX via C-interop.
NFR-2Ktor with the CIO engine (Netty/Tomcat unavailable on Native); REST + WebSocket endpoints.
NFR-3Okio for all file I/O (buffered streams) and memory-efficient NFO/XML generation — no java.io/nio.
NFR-4ktoml + kotlinx.serialization for typed TOML config.
NFR-5Subprocess abstraction (e.g. Kommand) over ffmpeg/ffprobe/mkvpropedit, capturing stdout/stderr for live progress.
NFR-6Frontend in Kotlin WASM rendering to the real DOM (kotlinx.browser + type-safe HTML DSL) — explicitly not Compose-on-canvas, for accessibility, SEO and native text.
NFR-7Tailwind CSS built via Gradle/PostCSS; dark mode; responsive.
NFR-8Docker Compose deployment: media volume rw, config volume rw, shared network with Jellyfin, restart: unless-stopped, run as non-root matching host media uid/gid.

5 · Delivery phases

Iterative, each phase independently verifiable before the next builds on it. Durations are rough.

Phase 1Infrastructure & backend foundation~2 weeks
  • Docker Compose with media/config volumes and shared Jellyfin network.
  • Ktor Native server on the CIO engine; health endpoint.
  • ktoml config load/save from the persistent volume; typed config classes.
Phase 2DOM frontend & API layer~3 weeks
  • Kotlin WASM project rendering to the real DOM; Tailwind via PostCSS.
  • App shell + Settings screen reading/writing config over REST.
  • WebSocket channel established; live status plumbing end-to-end.
Phase 3Domain engine & process execution~4 weeks
  • Okio-based NFO/XML generation with lockdata.
  • Subprocess abstraction over ffmpeg/ffprobe/mkvpropedit.
  • TMDB client; identify original_language; scan + media list + media detail.
Phase 4Cascade, triage & Jellyfin integration~3 weeks
  • Cascade resolver + editor; per-folder overrides; live preview.
  • Track reorder/default via mkvpropedit, ffmpeg fallback, dry-run.
  • Triage list for untagged/mismatched tracks; artwork download; Jellyfin /Items/{id}/Refresh.
Phase 5Automation & test regime~2–3 weeks
  • Blender-film fixture/download script with injected tracks + broken defaults.
  • Playwright-in-Docker integration tests with simulated clicks and visual snapshots.
  • Final validation, hardening, documentation.

6 · Out of scope / open questions

  • Auth — decided: Jellyfin sign-in (Jellyseerr-style), admins only. See §2.9 and the Implementation Plan.
  • Hardcoded movie/TV paths — decided: library paths are discovered from Jellyfin and mapped per-library (FR-C5–6). Static movies_dir/tv_dir config keys are removed.
  • Music / other media types — any Jellyfin library type (music, books, photos) can be discovered via FR-C5 but is marked "skip" by the operator if not relevant. Metadata handling for non-movie/TV types is out of scope.
  • Metadata providers beyond TMDB (e.g. TVDB, MusicBrainz) — future?
  • Undo / change history depth — is a per-file history log required, or is the NFO on disk enough?
  • Conflict handling when a file is edited outside Jellystructure after locking.
