A TV signs in from your phone

And a Sign in with ‹name› button on the phone, Ravilo Web, the desktop and the admin. Two halves, one visual language.

Round 2026-10-23-tv-signin · drawn in this repository · 97 PNGs · TV 1920×1080 · phone 412×915 and 393×852 · web 390 and 1440 · Mac 1440×900 · admin 1100×760

Every frame is built from one data file (ts-data.js) through one kit (ts-kit.js), so the pictures agree with each other by construction rather than by luck. The frames link the shipped stylesheets — design/ravilo/ravilo.css for the TV, design/ravilo/mobile/ravilo-phone.css (plus the desktop file) for the phone, web and Mac, design/app/wf.css for the admin — so every token, colour, radius and font in the pictures is the production one. Nothing is copied.

What is fixed, before any direction

  • Jellyfin is invisible to viewers. No frame on the TV, the phone, the web, the desktop or the four browser pages names Jellyfin, LDAP, Quick Connect, a plugin or a status code, in any of the three languages, failures included. The browser pages' address bar shows jellystructure's own return route. The admin frame is exempt and keeps its existing copy exactly as Login.kt has it.
  • The TV never shows a single-sign-on button. Single sign-on happens on the approving device. There is no frame in this round where a TV offers one.
  • Nothing is typed on the TV and the only focusable thing on the sign-in screen is Sign in with a password instead, drawn focused in every TV frame.
  • No countdown. The code is re-minted silently, so no frame shows time remaining.
  • No camera scanner inside Ravilo. The phone's own camera opens the link.
  • The shipped i18n/*.json wins wherever a string already exists. Twelve strings in this round are reused verbatim; the rest are new and their Danish and Faroese are drafts. The table at the end marks which is which.

1 · The TV — two directions

Recommended Direction A — “Two columns”

The QR on the left at 444 px, and the code, the instruction, the address and the TV's name stacked beside it in reading order. A viewer who can scan looks left; a viewer who cannot reads straight down the one column that concerns them. The password button sits bottom-left under the QR, focused.

Alternative Direction B — “One column, centred”

The same blocks stacked down the middle. It cannot hold the same sizes. With the 92 px brand row, the 168 px footer and 56 px of overscan margin, the stack has 764 lines; FR-5's other four blocks need about 460 of them, so the QR comes down to 300 px and the code to 80 px. That is the whole argument between the two directions and it is a measurement, not a taste.

What 444 px and 300 px mean in the room. A 55-inch set is about 122 cm wide, so 1920 px maps to ~0.64 mm per pixel. A's QR is ~28 cm across; B's is ~19 cm. The usual field rule for a phone camera is a QR side of roughly a tenth of the reading distance, which at three metres wants ~30 cm. A is a three-metre code. B is a two-metre code. On a 43-inch set A becomes ~22 cm and is already at the rule's limit — that is the smallest screen this size is honest on, and it is worth QA pointing a real phone at both.

What the no-QR state showed

The first render of tv-a-no-qr was the defect the brief predicted: with the QR gone, direction A's content sat jammed against the left gutter with two thirds of 1920 empty. A's premise is two columns, and with no QR there is no second column — so A's no-QR state is a centred single column, which is direction B's arrangement. The code grows to 136 px there, because it is now the only thing on the screen to read across the room.

Say it plainly: in the no-QR state the two directions are the same screen. That is a point in B's favour, and it is only visible because both were drawn.

The code's typography

Reused from design/ravilo/Play on a TV - Directions.html, §“The code, and why it looks like this”: JetBrains Mono, tabular figures so the string never reflows, grouped 3 + 3, and an alphabet with no 0, O, 1 or I. Raised from the prior art's 96 px to 112 px, because here the code is the screen's subject rather than a line in the corner of an idle receiver. tv-a-code-96 is the same frame at the old size, so the number is a choice on two pictures.

State (d), Add user — the answer the brief asked for

The brief asked whether the heading or the Back hint differs from state (a). Only the Back hint differs — Back returns to the profiles, beside the footer button. The heading, the code, the QR, the instruction and the TV name are identical. tv-ctx-profiles draws where it is reached from.

Three context frames, which propose nothing

  • tv-ctx-password — R175's shipped LoginScreen, unchanged, so the reviewer can see what “one press away” lands on.
  • tv-ctx-unreachable — the ordinary could-not-reach-the-server state FR-5 defers to. The brief's state list does not mention it; the house rule requires it of any surface with a socket. The words are the shipped login.error_unreachable.
  • tv-ctx-profiles — the picker, with Add user focused.

Where the row goes

FR-6 says “beside the account rows R304 placed”. Drawn below Change password and above Settings: the rows above it are about this account and this app, Settings is the drawer everything else falls into, and signing a TV in is an account action rather than a preference. In the account frames the new row carries one accent rule along its leading edge — that is a marker for the reviewer, not part of the design.

Decision 3 — one field, not six boxes

Recommended One field that groups as you type (ph-code-typed): it takes a paste, it survives a code of a different length if the alphabet ever changes, it has one focus target instead of six for a screen reader, and it is the shipped .fld control rather than a new one. The six-box alternative is drawn in both states (ph-code-boxes-empty, ph-code-boxes-typed) and does fit 412 px with the 3 + 3 gap — it is a fair option, just a more expensive one.

Continue is drawn shown and disabled until six characters are in, never hidden.

The confirm screen

FR-6's reason for naming the TV is “so a viewer can tell a code that is not on a screen in front of them”. That wants the code shown back as well as the name, so the TV sits in a card at the top with K7P 4QX beside it. Under the question is one supporting line — Your list, your languages and where you got to come with you — which is proposed (question Q2 below): the spec gives the question and the two buttons and nothing under them.

Not you? Switch appears only where the device has more than one profile, below a rule, with the active profile named beside it.

The five outcomes

ph-outcomes-strip is the whole set in one picture. One glyph, one sentence, one way on. The spec gives the first two word for word; the other three are proposed. “Couldn't reach the server” is not a new string — the shipped login.error_unreachable already says it.

“Get a new code” was wrong and is now “Enter a new code”. The TV fetches a new code by itself; this button cannot get one. All it does is return to the field so the viewer can type whatever the TV is showing now. A control says what happens when you press it.

3 · The Sign in with ‹name› button

Full width, above the username field, with an or divider before the fields — all of which decision 4 asked for and the pictures agree with. The glyph is a neutral globe, never a provider's logo: the operator chooses the name and we are given no artwork, so a mark would be invented.

Decision 4's lean moved, and here is why. The brief leaned to a filled button above the fields. Drawn, that put two filled gradient buttons on one screen — the provider button and the form's own Sign in — and the first render of ph-signin-two and admin-signin-two is a page with two equally loud primaries and no answer to “which one is the way in?”. One filled control per screen is the house rule.

The admin frame

admin-signin, -two, -bold, -none, each in both themes (the light- prefix). Reproduced class for class from Login.kt in wf.css; the only addition is the button. The page is the operator's, so Jellyfin stays on it. --blur: none is set on the frame, because backdrop-filter is production CSS on every admin card and breaks the screenshot render — the live admin keeps its glass.

What the shipped page needs, since it is one file. No hosted font, no second stylesheet, no image file. Concretely:
  • Inline <style> in the <head>, roughly 2 KB — the .ts-page block in tv-signin.css is the whole of it, and it declares its own colours rather than reaching for a token file.
  • Type. Either one embedded woff2 (sora.woff2 is ~30 KB and would want to be base64 in the page, taking it to ~40 KB) or a system stack. The frames are drawn with Sora first and a system stack behind it, which is what the page would do if the font is served from the same origin as a normal second request. Our recommendation: serve the woff2 from jellystructure's own origin and keep the system stack as the fallback — the page is on our host, so it is one extra same-origin request and not a network dependency, and the viewer sees the right face.
  • The wordmark as inline SVG (~700 bytes). It is already drawn that way here.
  • No image file at all. Every glyph on these pages is an inline stroked SVG.
  • The language comes from Accept-Language (en, da, fo), so the page is rendered server-side with one of three string sets — there is no client-side switch.

Open questions for Bárður

Q1 · “Approving on ‹name›'s phone…” can be wrong. The approver may be at a computer — web-desk-confirm is exactly that path — and FR-3 sends only approverName, not the device kind. The spec fixes these words, so they are drawn as written. Either the wire carries the kind, or the line drops the device: Anna is approving…. Needs a decision, and possibly an FR-3 field.
Q2 · The confirm screen's supporting line is proposed. The spec gives the question and the two buttons and nothing under them. Your list, your languages and where you got to come with you says only what is already true of a profile. Keep, change, or drop it and leave the question alone?
Q3 · Three outcome strings are proposed — already used, unavailable, and the two new browser pages (cancelled, unavailable). Listed in full in the string table below.
Q4 · The brief names Ravilo Web's host but not the backend's. FR-10 puts the four browser pages on a new route on the backend's public origin (<public_url>/sso/OID/redirect/<P>), which need not be the same host as ravilo_web_url. Rather than invent a second stand-in, those frames reuse ravilo.example.net — one stand-in doing two jobs, visibly. Name the second one and the pages get re-rendered in a minute.
Q5 · ravilo.css's Google Fonts @import blocks render-design.sh. The new renderer fails the run on any off-host request, so the TV set could not be rendered at all; earlier TV rounds used their own render.mjs, which had no such check. This round works around it with a four-line Content-Security-Policy in frames.html that permits file: and data: and nothing else, so Chromium refuses the import at the policy and the renderer never sees a request. That belongs in the lane, not in a round — either the script grows a flag, or ravilo.css loses the line the way the served admin CSS already has. Until then every round that links ravilo.css needs those four lines, and a round that does not know that cannot render the TV at all.
Q6 · The signed-out arrival says nothing about the TV that is waiting. In web-arrive-signed-out a viewer who just scanned a QR lands on a bare sign-in screen; the code is kept, but nothing on the screen says so. A one-line banner would fix it, and the brief says not to redesign the sign-in screen — so it is a question rather than a drawing.
Q7 · “This account can't use Ravilo” is a dead end. Per the spec it carries no call to action, which is right if there is nothing the viewer can do. Worth confirming that a Try a different account link is deliberately not wanted.
