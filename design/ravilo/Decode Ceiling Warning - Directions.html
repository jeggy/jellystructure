"This might not play well on this TV"

Until Dawn stuttered on stue TV and got abandoned mid-watch — the third stutter on that TV in three weeks. The research report (ravilo-per-device-decode-ceiling-warning-2026-09-02.md) found that the measuring half of the owner's proposal already exists: Phase 177 / R216 read the decoder's own declared ceiling and force a transcode above it. Three things stand between that and a warning.

1 · It wasn't Ravilo

The stuttering session was Wholphin, negotiating straight against Jellyfin with its own device profile. Nothing we design here can reach it. Ever.

2 · Nothing is written down

The ceiling is computed fresh inside one PlaybackInfo call and thrown away. ravilo_device has no column for it, so no detail page can ask.

3 · It reverses an invariant

R216: "No user-visible setting, ever… the viewer's experience is that playback simply works." A capability warning is the thing that line was written to prevent.

The question underneath all three

The report frames this as a warning — this file may be too much for this TV. But if 177/R216 are working, that isn't what happens. The server sees the ceiling, refuses the direct play, and Jellyfin re-encodes: the picture is fine and the start is slow (~20 s cold, measured in the buffering-states report). The failure the viewer actually experiences is a wait, not a stutter.

So the honest signal isn't a capability warning at all — it's an expectation. "Slow to start on this TV" is true, needs no numbers, offers nothing to configure, and doesn't teach the viewer the words bitrate or transcode. It keeps the spirit of R216's invariant while admitting the one thing "playback simply works" currently gets wrong. Every direction below is judged against that.

What none of these can do: warn about, or protect, playback that doesn't go through Ravilo. If the household keeps using Wholphin on stue TV, last night happens again with every direction here, including D. That belongs in the spec's non-goals in the first paragraph, not a footnote.

Where the directions come from

The report offers A (keep the invariant) · B (narrow outcome-only heads-up) · C (full reversal). B's placement was left open (§6.3: badge / banner / gate), and that's a real fork — so B splits in two here. Mapping: A=report A, B and C=report B, D=report C.

The sentence

§6.4 asks for plain language that never says bitrate, codec, transcode, Dolby Vision or HEVC. Harder than it sounds: most candidates either smuggle a quality claim back in or promise something we can't verify.

Ship
Slow to start on Stue TV. Give it a moment after you press play.
Describes what will actually happen, and only that. No claim about picture, no jargon, no implied fault. The second sentence is the whole "action" — it tells you the one useful thing to do, which is wait. Names the device.
No
This title may not play smoothly on Stue TV.
The report's own wording, and the obvious first draft. It predicts a stutter — but if 177/R216 are live, the file gets re-encoded and plays smoothly. We'd be warning about the exact failure we already prevent, and "may" makes it unfalsifiable.
No
Stue TV can't handle this file at full quality.
"Full quality" is a quality control by implication — the viewer's next move is to look for the setting that turns it up. That's the door R216 closed deliberately.
No
Better on Bedroom TV.
Tempting, and the data almost supports it. But it needs a second measured device, a claim that the other TV is free, and it turns a per-title note into household logistics. Park it — if it ever ships it's its own phase.

Naming the device

Yes — "Stue TV", the name the owner gave it during pairing, because a three-TV household needs to know which one is being talked about. Fall back to "this TV" (phone: "this phone") when the device has no user-set name; never show a model string like BRAVIA VH21 to a viewer.

Three strings, all new, all needing da/fo — the first new player-adjacent copy since R218. Keep it to three: the sentence, the no-name fallback, and the phone fallback.

When it appears — and when it must not

§6.1 and §6.2 ask whether to trust the decoder's number alone or wait for corroborating history, and whether link quality belongs in the signal. These are the two decisions that determine whether the feature is trusted or ignored.

The ceiling decides whether

The device's recorded limit against this file's bitrate, on Phase 177's own 0.9 × ceiling predicate — one comparison, two consumers, so a note never appears without a re-encode behind it.

That device's history decides how sure

Has this device actually started this file before, and how long did it take? That's what turns a prediction into a measurement — and it's per device, because the same file on the bedroom Shield is a different answer.

The backend computes the whole verdict; Ravilo renders a sentence. The client gets a resolved playbackNote on the detail payload — device name, confidence, and a number of seconds when one has been measured — and displays it or displays nothing. No thresholds, no bitrates and no ceilings cross into the client, which is both R180's rule and the constitution's frontend renders server-pushed state only. It also means retuning the margin, or getting smarter about history, ships without touching Ravilo.

The payload, and the two things it can say

playbackNote: { device: "Stue TV", basis: "measured" | "expected", seconds: 20 }
// absent ⇒ the page says nothing. Not a state, not an empty slot.

measured
Slow to start on Stue TV. The last few times it took about 20 seconds.
This device has started this file before and the backend timed it. The number is the strongest thing we can say and the least arguable — it's not a prediction, it's what happened here.
expected
Slow to start on Stue TV. Give it a moment after you press play.
The ceiling predicate fires but nobody has played it on this device yet — the exact case Until Dawn was. No number, because we'd be making it up.

Why history is worth the complexity: the note earns its place the first time a viewer reads "about 20 seconds", waits 20 seconds, and is right. A house that learns the sentence is accurate stops treating it as noise — and that is the difference between this feature working and being ignored.

History may only ever strengthen the note — never toggle it. This is the rule that keeps QoE's flicker problem out: whether the note shows is decided by the ceiling alone (deterministic, same on every visit); history only chooses which sentence and supplies the seconds. So a bad Wi-Fi night can add a number but can never make the note appear or disappear, and a single outlier session can't move it — the seconds are a median over that device's recent starts of this file, re-derived only when a session completes, and rounded to something honest (5 s steps) so it doesn't twitch between visits.

Silent in all of these

  • Ceiling not measured yet — the device hasn't run a Ravilo session since R216. Unknown is not "fine", but it isn't a warning either.
  • File bitrate unknown — not in Track today (§4); until it's carried through, no comparison, no badge.
  • Under the threshold, obviously — which is the overwhelming majority of the library.
  • Non-Ravilo clients — invisible to us, and the page says nothing about it (§6.8). A viewer who runs two Jellyfin apps on one TV is not a case worth adding a sentence for; the admin device row is where that gets explained.

Series and multi-episode files (§6.5)

A ceiling is per device, a bitrate is per file — so this is never a property of a series. The badge belongs to the thing that plays: the episode row in the rail, not the series hero. A Phase 149 combined S01E01–E03 row is one physical file, so it gets one badge for the row, and expanding it must not repeat the badge three times.

Practically this means a movie shows it in the hero and a series shows it on rows — worth being explicit about in the spec, because the naive implementation puts it in both heroes and the series one would be wrong for every episode with a different source.

What I'd ship

A + B′ — decided, and B′ is now built into the mockups. Persist the ceiling and show it on the admin device row (A, a prerequisite regardless), and put one plain line above the Play button on the Ravilo detail (B′), computed backend-side per device from the recorded ceiling and that device's history. Reject the gate (C) because it has nothing to offer but dismissal, and reject the numbers (D) because R180 and R218 already decided that question.

The invariant survives, honestly. R216 says no user-visible setting — nothing here is settable, adjustable or dismissible. R180 says no codec names or delivery cues — nothing here names a codec, a bitrate or a delivery method. What we add is one true sentence about how long the next 20 seconds will feel, which is the one thing "playback simply works" currently gets wrong about this TV.

Pin these down before anyone builds

  • One predicate, two consumers. The badge and Phase 177's transcode decision compare the same two numbers with the same 0.9 margin. If the margin is ever retuned, both move together.
  • Whether ≠ how sure. The ceiling decides whether the note shows; that device's own history decides which sentence and supplies the seconds. History can never toggle it on or off, so it can't flicker.
  • The client renders, never computes. One resolved playbackNote per file per device on the detail payload; absent means silence.
  • No action, by design. Not focusable, not dismissible, no "don't show again". There is nothing to configure and pretending otherwise would be worse.
  • Per file, not per title. Movie hero; series episode rows; one badge per combined multi-episode row.
  • Noir drops the tint, keeps ink and weight — R221's precedent, same reason.
  • Non-goal, stated up front: nothing here reaches Wholphin or any other Jellyfin client. Not a limitation to be fixed later — architecturally impossible (§2).

Still open

  • Where the file's bitrate comes from (§4) — a bitRate field on Track at scan time, or a live MediaSources read at render time. Scan-time is cheaper per page view and works offline but is stale for anything just added; the live read is always right and might piggyback a fetch DetailStore already makes. Needs a backend answer, and it decides whether this is one phase or two.
  • Is one 60 Mbps decoder enough to design a fleet feature from? R216's own open question #1: other OEMs may report optimistic numbers. A lying ceiling means a badge that never fires (harmless) or one that fires on everything (feature dies of distrust). We can't test it in this house.
  • Has the R216 build actually been installed on the stue TV Ravilo? The report can't tell from the repo. If it hasn't, then the transcode fallback isn't live either — and the honest copy for that state is the rejected "may not play smoothly", not "slow to start". Confirm before writing the spec.
  • Does the owner want the admin half at all, or only the Ravilo line? A is genuinely useful alone and could ship first as a small admin-only phase.
