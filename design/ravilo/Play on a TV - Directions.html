Play on a TV — one glyph, three tiers

The brief of 2026-09-18 (design-brief-screens-and-web-install) answers the owner's picture: an iPhone installs the web app and streams to the Samsung TV. The TV runs a receiver-only Ravilo app with no navigation (R264); the phone drives it through the backend (236), so the phone can be closed and the picture continues; and everything hides behind the same Cast glyph (R265). Two things this brief reverses: the device picker is now Ravilo's own sheet, not the platform's, and AirPlay is drawn after all — one tier down, with a notice.

This canvas draws §B (the sheet, ten states), the two round-1 questions as marked options, the AirPlay-active player, §C's receiver frames, and §D's admin table. Nothing here is built into Ravilo Mobile.html or Ravilo Receiver.html yet: §A (the install card, the notice, the icons) and §C1 need no pick and can be built straight away — say the word and they go in next.

Decided in the brief — the same in every frame

Q1 · decided: the footnote

a · Full row, notice on its second line — drawn, not chosen

The caveat is in the interface at the moment of choosing, in words a parent can act on: the TV stops when you close the app. It costs one line of sheet and reads as a normal, supported route that happens to have a condition — which is exactly the truth.

It also survives the case the tier exists for: grandparents' AirPlay-2 TV, nothing else in the room, nobody to ask.

Drawn, kept on this canvas2 lines of sheet
b · Footnote link under the collapsible — the owner's pick, and what is built

Cheapest and quietest: one 13 px line, unmistakably a lesser route. But the caveat is compressed into a parenthesis, and a parenthesis is what people skip — the first time the picture dies on close, the app looks broken rather than honest.

It also sits below the collapsible, so on a household with many TVs it is off the bottom of the sheet entirely.

Chosen 2026-09-1846 px target keptscreens.airplay_footnote
So the caveat moves, it does not vanish (R270 FR-R270-2): the full sentence — your phone has to stay on and in Ravilo — is shown as the connecting bar the moment an AirPlay session starts, and verbatim in the admin's Connections help text. A parenthesis is what people skip; a bar at the moment it becomes true is not.

Three things hold either way. The row is below a heavier hairline and in quieter ink; tapping hands over to Apple's own picker, which we do not redraw; and while AirPlay runs there is no mini bar and no remote — the phone's own player is the remote, drawn at §4.
One open question the device must answer (R265 OQ 1): does a standalone iOS web app keep an AirPlay session alive when merely backgrounded? The notice is written for the worst case; if the test passes it can soften to "…stays on" — which is a string change, not a redesign, in both directions.

C · Code anatomy — read from a sofa

The code, and why it looks like this

218 already mints it: six characters, server-side, valid until it expires, re-minted on expiry, and a paired phone never sees it again.

  • 96 px glyphs in 1920 space — a shade over the brief's 72 px floor, because this is read across a living room, not from a keyboard.
  • Tabular figures, so the string never reflows as characters land, and 218's alphabet already excludes the ambiguous ones (no O/0, no I/1).
  • Bottom-right, the TV's name bottom-left. A household with two receivers must be able to tell which screen it is typing at, and the name is the only thing that answers that.
  • No QR, no camera. R264's input surface is the backend and the TV remote; a phone camera is neither, and the code is faster than a scan at sofa distance.
  • Visible to anyone in the room, by design. Fine for a household (R264 OQ 3); it is the guest-mode TV, if one is ever wanted, that would change this.
Idle carries no artwork — mark, name, code, one sentence. That is FR-R264-7 (a 2013 stick and a 2019 Samsung must both hold it) and it is also the honest screen: nothing is playing, so nothing should be pictured.

§C0 · found missing 2026-09-18 · owner's catch · now R269, decided

Before any of §C can happen: the TV has to be told where Ravilo is

R264 has a hole. FR-R264-1 says the app enrols with 218's hand-off code and FR-R264-2 says idle always shows a pairing code — but a code is minted server-side, so neither is possible until the TV can reach a server, and nothing in the phase says where that address comes from.

Why the Chromecast receiver never needed this: it is served by the backend at /cast/, so its own origin is the server — it can ask before it can be configured wrong. A sideloaded Tizen .wgt is a local file with no origin at all. It boots knowing nothing.

So the receiver gets one screen the household sees exactly once, and it is not new work: it is R225/R226's ServerSetupScreen with R175's on-screen keyboard, which the TV client already ships and this household has already used. Drawn below in the states that actually occur.

What this costs, and what it is not allowed to become

One screen, once, on a TV that otherwise has no navigation at all. That exception is the whole design risk, so it is fenced:

  • It is reached only when there is no server — never from the idle screen, never mid-playback, and never as a menu. A configured receiver has no route back to it (see the question below).
  • The scheme is not a question. R226 already settled this: type a host, Ravilo infers https:// and falls back to http:// on a private address. No toggle, no dropdown.
  • It is the last thing the app draws before it becomes a renderer. After Forbind, the token is stored on the TV and every subsequent screen comes from the backend (FR-R264-5) — including the pairing code, which only now can exist.
  • Idle names the server from then on (C1c): one quiet mono line under the TV's name. It is the only way a household can see that a TV is pointed at a server that moved.
Two states that read the same today and must not. "Can't reach the server" (C1b) means configured, unreachable, retrying — do nothing, it will come back. No server at all means type an address. R264's FR-R264-6 currently uses one sentence for both, which sends a household hunting for a network fault when the app simply was never set up.
Considered and rejected: discovery instead of typing. mDNS/Bonjour from the TV would remove the keyboard, but Tizen 5.0's web runtime has no usable mDNS, the phone side already refused LAN discovery as a non-goal (R265), and a receiver that sometimes finds the server is worse than one that always asks once. Rejected for the same reason the phone's "on this network" is the server's judgement and not the phone's.

Two questions this opened — both answered

1 · How does a household change the server later, on an app with no navigation?

a · A hold on the idle screen. Hold Back (or OK) for three seconds on idle and the setup screen returns, with the current address in the field. Nothing is drawn to advertise it; it is the same class of affordance as a factory reset.

b · Nothing at all. Reinstall, or clear the app's data from Tizen's own settings. Honest, zero surface, and brutal the first time the server's address changes.

c · From the phone. Cannot work: the phone reaches the TV through the server it is trying to replace.

Chosen: a · hold Back three secondsc is impossible
2 · Does the code screen wait for the server, or show a stale code?

a · Wait. No code until the server answers; the screen says Prøver at få forbindelse… under the mark. A code that cannot be redeemed is worse than no code, because the viewer types it and gets "That code didn't work" on the phone — a failure that points at the wrong device.

b · Keep the last code. Faster in the common case (the server is up, the socket blipped) and 218's codes outlive a blip.

Chosen: a · wait, and say so
Spec consequence. R264 is Planned and dev-authored, so this is written as R269 rather than edited into it: the receiver needs a server before it can pair — the setup screen, the inferred scheme, the two distinct no-server states, the server line on idle, the return path, and the ordering rule (server → code → pair). It supersedes FR-R264-2's "always shows its code" and FR-R264-6's single no-server sentence. Next free after it: 238 / R270.
