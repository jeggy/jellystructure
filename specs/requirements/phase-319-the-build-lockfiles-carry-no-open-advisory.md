# Phase 319 — The build's lockfiles carry no open advisory, and none of them ever reached a user

> Found 2026-10-15 by the CI watch (DEB-1212 → DEB-1219): GitHub's `Dependabot Updates` job has failed
> on every run it keeps, and the repository shows **46 open Dependabot alerts — 2 critical, 29 high,
> 11 medium, 4 low** — all of them in the two Kotlin-generated yarn lockfiles. The repository is
> public, so that count is visible to anyone.

## Scope

The root `build.gradle.kts` (yarn resolutions on the Kotlin/JS and Kotlin/Wasm yarn roots) and the two
lockfiles Gradle generates from it, `kotlin-js-store/yarn.lock` and `kotlin-js-store/wasm/yarn.lock`.
No Kotlin source, no wire, no schema, no UI — **there is no surface**, so no design round and no
device test.

What this phase supersedes: nothing. What it leaves to the owner: the repository's Dependabot
settings and the dismissal of any alert (§FR-319-5).

Number allocated from [`STATUS.md`](../../STATUS.md) on 2026-10-15: the admin table's highest row was
318, so 319 was the next free one.

## What was found (2026-10-15)

### Nothing advised reaches a user

- **45 alerts are in `kotlin-js-store/yarn.lock`, 1 in `kotlin-js-store/wasm/yarn.lock`.** Dependabot
  labels every one `runtime`; that label carries no information here, because there is no
  `package.json` beside either lockfile to tell it what is a dev dependency.
- **The Wasm lockfile holds exactly two packages:** `@js-joda/core` 3.2.0 (kotlinx-datetime) and `ws`
  8.20.1 (Ktor's JS client, which pins it exactly). The Wasm *toolchain* — webpack, webpack-dev-server
  — is not in it: the Kotlin Gradle plugin installs it under `~/.kotlin/kotlin-npm-tooling/`, outside
  the repository.
- **The JS lockfile is the Kotlin/JS toolchain** for `ravilo-cast`, `ravilo-screen`, `ravilo-tizen`,
  `ravilo-receiver-core`, `ravilo-i18n` and `shared`: webpack 5.101.3, webpack-dev-server 5.2.3,
  Kotlin's karma fork, mocha, and their transitive trees. The only non-dev dependency any generated
  package declares is `ws`.
- **`ws` is the only advised package any production bundle contains, and what it contains is ws's
  browser stub** — a separate chunk of a few hundred bytes whose whole body throws *"ws does not work
  in the browser"*, in the Cast, screen and Tizen bundles. The admin `jellystructure.js` and Ravilo
  Web's `ravilo.js` contain none of it. The `ws` advisory is a memory-exhaustion on a Node process
  *receiving* frames; in a browser the platform's own `WebSocket` is used. (Measured by grepping the
  production bundles in a working checkout; FR-319-4 repeats it on fresh builds.)
- **No production image runs Node.** The backend, `ravilo-web` and `ravilo-screen` Dockerfiles install
  Node only in their `builder` stage; each runtime stage is `debian:bookworm-slim` serving through the
  backend or `web-static-server`. webpack-dev-server, express, body-parser, socket.io and engine.io
  never run on prod.

So the exposure is **build time and a developer's own machine** — the dev server behind `runDev`,
karma in the browser tests, terser during a production build — and the public alert count. Severity
for users: none.

### Why the Dependabot job fails, and why no file in the repository can fix it

Dependabot security updates are switched on for the repository, so every new advisory starts a
`security` job on the npm updater. Each one aborts at file fetching with
`/kotlin-js-store, /kotlin-js-store/wasm not found`. The directories exist; the **manifest** does not.
Dependabot's yarn support reads a `package.json` beside the lockfile, and Kotlin's layout keeps the
lockfile alone — the manifests are generated into `build/js/` and `build/wasm/` at build time.

That means Dependabot can never open a pull request here. The only in-repository change that would
let it is a committed `package.json`, and this phase rejects that: it would be a second,
hand-maintained source of truth beside Gradle, and a Dependabot pull request against it would edit a
lockfile that Gradle regenerates and checks on its own terms. **The remediation path for an alert in
this repository is Gradle — a resolution, and a regenerated lockfile.**

### Zero alerts is not a clean toolchain

The Wasm toolchain under `~/.kotlin/kotlin-npm-tooling/` is pinned by the Kotlin Gradle plugin and is
invisible to Dependabot. On 2026-10-15 it held webpack-dev-server 5.2.3 and `ws` 8.18.3 — the same
versions the JS lockfile's alerts are about. It moves with a Kotlin upgrade, not with this phase.

## Requirements

### FR-319-1 — Pinned through Gradle, regenerated by Gradle

Every advised package is raised through the Kotlin yarn root extensions' `resolution(...)` — the
JS yarn root for `kotlin-js-store/yarn.lock`, the Wasm yarn root for `kotlin-js-store/wasm/yarn.lock` —
declared once, in the root build script. The lockfiles are then regenerated by Gradle
(`kotlinUpgradeYarnLock`, `kotlinWasmUpgradeYarnLock`) and committed with the build-script change in
one commit. **The lockfiles are never hand-edited** — each says so in its own header.

Each resolution carries a short comment naming why it is there (the advisory's package, toolchain
only), so whoever next upgrades Kotlin can tell which resolutions the new plugin has made redundant
and drop them.

### FR-319-3 — A major crossing is kept only if the toolchain still works

The three rows marked *yes* are kept only if every check in FR-319-4 passes with them. If one breaks
the toolchain, that one resolution is dropped and a **dated note under this requirement** records the
package, the failure seen, and that its alert stays open for that reason. The engineer does not
dismiss the alert; that is the owner's (§FR-319-5).

> **Note, 2026-10-15 (DEB-1219).** All three major crossings were kept: `serialize-javascript` 7.1.2, `diff` 8.0.4,
> `uuid` 11.1.1, with the four production distributions building (FR-319-4). Nothing is recorded here as left open
> but `braces`.

### FR-319-4 — The toolchain still builds and tests, and no npm package newly ships

All of these pass on the commit that changes the lockfiles:

- the production distributions: the admin frontend, Ravilo Web, the Cast receiver and the screen
  receiver (`wasmJsBrowserDistribution`, `:ravilo-web:wasmJsBrowserDistribution`,
  `:ravilo-cast:jsBrowserDistribution`, `:ravilo-screen:jsBrowserDistribution`);
- the karma-driven tests: `:shared:jsTest` and `:ravilo-i18n:jsTest`. CI runs no JS or Wasm test
  task, so this is the only run the upgraded karma, mocha and `diff` get; if the build host has no
  headless browser for karma, the commit message says so rather than the check being skipped
  silently;
- **the shipped-bytes check:** the npm modules present in those production bundles are the same set as
  before — `@js-joda/core` in the Wasm bundles and ws's browser stub in the JS ones, nothing else.
  The check is a grep for the toolchain's own markers (`permessage-deflate`, `webpack-dev-server`,
  `sockjs`, `socket.io`) returning nothing, and is written into the commit message with its numbers;
- CI green on the pushed commit, read from the Publish run per `CLAUDE.md`.

> **Note, 2026-10-15 (DEB-1219) — what the check could and could not prove.**
> - The four distributions build on the new lockfiles, and the shipped-bytes grep returns `0` for every
>   toolchain marker in all four; the browser-stub marker is present in the Cast and screen bundles only and
>   `js-joda` in the two Wasm bundles only, as before.
> - **`:shared:jsTest` and `:ravilo-i18n:jsTest` fail on the commit before this one as well**, identically:
>   `:shared:compileTestKotlinJs` does not resolve `kotlin.test`, and `:ravilo-i18n:jsBrowserTest` stops with

>   mocha and `diff` are not exercised by any test**. That is a standing gap in the JS test targets, not a
>   result of this phase, and it is reported on the task rather than fixed here.
> - The Cast and screen receiver bundles are byte-different from the previous commit's (toolchain: terser,
>   webpack runtime), so they go on the QA queue.

### FR-319-5 — The Dependabot job is a repository setting, not code

Nothing in this phase makes `Dependabot Updates` stop failing, and nothing can (see *Why the
Dependabot job fails*). Two decisions belong to the owner, carried by the CI watch, and this phase's
engineering does not wait for either:

1. **Recommended: turn *Dependabot security updates* off and keep *Dependabot alerts* on.** The alerts
   stay the signal; FR-319-1's resolutions stay the remedy. Left as it is, every new advisory in
   either lockfile produces one more failed run, and the CI watch files it again.
2. **Dismissing `braces`** (no fix exists upstream; toolchain only) and any leftover FR-319-3 records,
   with the reason *"vulnerable code is not used in production — build toolchain only"*.
