# Phase 318 — The container speaks ASCII, and every MKVToolNix call pays for it

> Found 2026-10-13 (DEB-722 → DEB-833 → DEB-848) while answering a question phase 317's amendment had
> left open: *who truncates `mkvmerge -J`?* The answer is neither of the two suspects. The backend
> container has **no `LANG` and no `LC_*`**, so every process it spawns runs in the C locale, and every
> MKVToolNix tool — `mkvmerge`, `mkvpropedit`, `mkvextract` — mishandles a non-ASCII path or a
> non-ASCII string it must emit. This is a Faroese and Nordic library: `ø æ á ð í ó ú ý` are ordinary,
> and **1 247 of 4 142 matroska files (30.1 %)** carry one in their path.

## Scope

One environment variable, one health check, and the record of what the missing variable cost. The
phase is deliberately small: it changes no parser, no schema and no advice. The parser work the same
discovery touches belongs to phase 317 and stays there (FR-317-21 to FR-317-26), because 317 is where
a truncated identification document is read.

What this phase supersedes: nothing. What it corrects: the **environment**, not a specification. That
distinction decides the whole shape of §FR-318-5 — the shipped phases whose calls have been failing
were specified correctly and are not amended.

Number allocated from [`STATUS.md`](../../STATUS.md) on 2026-10-13: the admin table's highest row was
317, so 318 was the next free one.

## What is wrong, measured

`/proc/1/environ` of the live backend (`/app/jellystructure`) carries **only `PATH`**. The runtime
image is `debian:bookworm-slim` and its `Dockerfile` sets eight `ENV` lines, none of them a locale.

### Reproduced without the library, in the backend's own image

Both failure classes reproduce in a throwaway container from `jellystructure-backend:latest`, with
no mounts and no network, on two one-second files generated by `ffmpeg` in `/tmp`. **No library file
and no title is needed to see this, or to prove it fixed** — which is why the acceptance below is
written against the synthetic pair and not against the household's own files.

| Case | `LC_ALL=C` | `LC_ALL=C.UTF-8` |
|---|---|---|
| **Non-ASCII path**, `mkvmerge -J` | **exit 2**, 115 bytes: a *valid JSON error document* — `{"errors":["The file '/tmp/f' could not be opened for reading: open file error."],"warnings":[]}`. Note the path in the message is itself cut at the first non-ASCII byte. | exit 0, 2 188 bytes, the complete document |
| **ASCII path, non-ASCII track name**, `mkvmerge -J` | **exit 0**, 2 111 bytes, **empty stderr**, and the document is cut mid-string: it ends `"track_name": "F` and stops. | exit 0, 2 235 bytes, complete |
| **Non-ASCII path**, `mkvpropedit --edit track:a1 --set language=fao` | **exit 2**, `Error: The file '/tmp/f' is not a Matroska file or it could not be found.` **The file is not written.** | exit 0, *"The changes are written to the file. Done."* |
| **Non-ASCII path**, `mkvextract … timestamps_v2` | **exit 2**, `Error: Unknown mode '/tmp/f'.` — the mangled path is taken as the mode argument | exit 0 |
| **Non-ASCII path**, `mkvmerge -o … <input>` (a remux) | **exit 2**, could not be opened for reading. **Nothing is written.** | exit 0 |
| **Non-ASCII path**, `ffprobe -show_entries …` | **exit 0**, correct output | exit 0, identical |

`mkvmerge v74.0.0`. `locale -a` inside the image lists exactly `C`, `C.utf8`, `POSIX`, and
`LC_ALL=C.UTF-8 locale` reports `LC_CTYPE="C.UTF-8"` with no complaint — so the spelling `C.UTF-8` is
accepted and **cannot fail closed** in this base image. That was the first thing DEB-848 asked to
confirm rather than assume; it is confirmed.

### The two classes, and why one of them is invisible

- **A non-ASCII path fails loudly** — non-zero exit, a message on stdout or stderr. Every writer
  therefore **fails closed**: nothing is written, nothing is half-written, and the operator gets an
  error. The error merely blames the wrong thing (*"is not a Matroska file"* for a perfectly good
  matroska file).
- **A non-ASCII string in the output truncates silently** — exit 0, empty stderr, and a document that
  is valid up to the first non-ASCII byte of the first string that carries one and absent after it.
  Nothing downstream can tell this from a short file. This is the class that cost 317 its command,
  and the 3 844 bytes of the real file were never buffer-aligned evidence of anything: the cut falls
  wherever the first non-ASCII character falls.

### What it has cost, per call site

ffmpeg and ffprobe are **immune** — proven in the table above, and the reason is that they open paths
as raw bytes. MKVToolNix converts its arguments through the locale's charset. So the blast radius is
exactly the MKVToolNix calls, and no others:

| Call site | Tool | What the C locale did to it |
|---|---|---|
| `AvSyncService.kt:566` (`readMkvAudioIds`, FR-317-5) | `mkvmerge -J` | both classes. **135 of 490 measured matroska rows carry a `NULL` id map, and 92 of 92 non-ASCII-path files lost theirs — no exceptions.** Phase 317's missing command. |
| `FileFixService.kt:191` (`probe(withUids = true)`) | `mkvmerge -J` | an empty uid map on a non-ASCII path, so no `JELLYSTRUCTURE_COPY_OF` uid to tag a copy with |
| `FileFixService.kt:431` (314c *Remove*) | `mkvmerge -J` | `copyTrackIds` returns empty → the `ids.isNotEmpty()` guard skips the whole removal. **Fails closed and silently**: the file is untouched and no finding is raised. |
| `FileFixCommands.appendTracks` / `removeTracks` / `dvMux` | `mkvmerge -o` | refuses the input; `FixOutcome.Failed("mkvmerge failed: …")` reaches the admin |
| `FileFixCommands.dvTimestamps` | `mkvextract` | refuses; `FixOutcome.Failed("mkvextract couldn't read the timestamps")` |
| `TrackRoutes.kt:157/256/368`, `MediaRoutes.kt:1243/1311`, `TriageRoutes.kt:187/250` | `mkvpropedit` | **the admin's in-place track writes — language, default and forced flags, titles — have been refusing every non-ASCII-path matroska file**, with a message that says the file is not a matroska file |
| `TrackCoverageService.kt:175/192/206` (phase **255**) | `ffprobe` only | **nothing. 255 is not in the blast radius.** |
| `WorkFileSweep.kt:41` | `find` | nothing; `find` is byte-transparent |
| `MkvLayout.kt:51`, `MediaRoutes.kt:1109` and every other *printed* command | — | nothing. A command we print is run in the operator's own shell, under the operator's own locale. |

**The correction DEB-848 needs, recorded here because it changes what is re-measured:** the routing
note predicted phase 255's track coverage was taking the same damage, on the grounds that it shares
`captureShell` and `FileFixCommands.identify`. It shares `captureShell`; it does **not** call
MKVToolNix. 255's three probes are `ffprobe`, and `ffprobe` is proven immune on the same file in the
same locale. **255's stored rows need no re-measurement, and nobody should spend a sweep on them.**

## FR-318-1 — The image declares a UTF-8 locale, and the compose file can do it without a rebuild

- **`ENV LANG=C.UTF-8` in the runtime stage of `Dockerfile`**, beside the existing eight `ENV` lines.
  This is the durable half: every build of every stack — prod, the dev stack, `docker-compose.test.yml`,
  the GPU and avsync overlays, and anyone else's deployment of the public image — gets it, and no
  compose file has to remember.
- **`LANG`, not `LC_ALL`.** `LANG` is the lowest-precedence setting in the chain, so it is a default a
  call site can still override; `LC_ALL` overrides everything including a future per-call need. There
  is no case today that wants a non-UTF-8 locale, so the weaker variable is the right one.
- **`environment: - LANG=C.UTF-8` on the backend service in `docker-compose.yml`** as well. Not
  redundancy for its own sake: it is what lets the fix reach a running deployment by recreating the
  container from the image it already has, without waiting for a rebuild. The two can never disagree —
  they are the same value.
- `C.UTF-8` is **confirmed present and accepted** in `debian:bookworm-slim` (`locale -a` → `C.utf8`;
  glibc ≥ 2.35 accepts the `C.UTF-8` spelling). No `locales` package, no `locale-gen`, no image size
  cost.
- The sidecar image is **not** changed: it reads paths through Python, which coerces the C locale to
  `C.UTF-8` for itself and its children (PEP 538), and it demonstrably measured all 92 non-ASCII-path
  files without trouble.

**An environment change takes effect only on a container recreate.** That is the owner's call, with
the rest of the deploy.

## FR-318-2 — The backend says so, rather than failing quietly for another unknown number of months

The cost of this bug was not its size; it was that **nothing anywhere said a word**. One `mkvmerge`
exited 2, one exited 0 with half a document, and the backend treated both as "a file with nothing to
report". That must not be possible to repeat for the price of one check.

- **At startup, one `WARN` on the integrity channel** if the effective character encoding is not
  UTF-8 — read from `nl_langinfo(CODESET)` after the usual `setlocale(LC_ALL, "")`, which is the
  question that actually matters and is cheaper to get right than parsing the `LC_ALL`/`LC_CTYPE`/`LANG`
  chain by hand. The line names the encoding it found and the consequence in the phase's own words:
  that MKVToolNix cannot open a path outside ASCII, and that roughly a third of this library's
  matroska files have one.
- **One health check**, beside `Server.kt:584`'s existing `which mkvpropedit` check and in the same
  shape. Green when the encoding is UTF-8; red with the found encoding when it is not. A red check
  here is not advice about tidiness — it means a third of the library cannot be written to.
- **No new config key.** There is no reason to make a UTF-8 locale optional, and a setting for it
  would be one more thing to read wrong.
- The check reports; it does **not** call `setlocale` to paper over the environment. A process that
  silently repairs its own environment hides exactly the class of fault this phase exists to surface,
  and the fix belongs in the image where every future call inherits it.

## FR-318-3 — The stored damage, and what refills it

- **Phase 317: 135 rows.** A measured matroska row with a `NULL` id map keeps showing advice with no
  command for ever, because `recheckUnchanged = false` means no sweep revisits a file that already
  has a row and `scope = "missing"` will not re-queue it. They are refilled by a **one-off forced
  re-check** — the Checks card's existing ↻ with `force=true`, or one pass over exactly those rows.
  Roughly 135 files at the measured 10–25 s of GPU each is **under an hour on GPU 1**, once.
- **FR-317-23's rule stands**: the `avsync` lane does **not** gain a permanent re-probe pass. The
  premise of that rule — the GPU measurement is the expensive part and it succeeded — is still true;
  a one-off recovery of a known finite set is not a standing mechanism.
- **Phase 255: nothing.** Proven immune above.
- **The write paths: nothing to refill.** Every MKVToolNix *writer* failed closed — it refused the
  input and wrote nothing — so there is no half-written file anywhere, and no file was ever written
  by this backend under a mangled path. What was lost is **actions that did not happen**: track
  writes the admin reported as failed, and 314c removals that were skipped without a word. Nothing
  can enumerate those after the fact, and nothing needs to: each one is simply available again the
  moment the locale is right.
- **The one quiet write path to confirm, not assume**: 314c's *Remove* skipped silently
  (`ids.isNotEmpty()` guard). Whether that ever ran against a non-ASCII-path file is unknown and
  unknowable from the data. It is listed here so the next reader does not have to re-derive that it
  was harmless.

## FR-318-4 — The sweep is held until the locale is right

- **Locale first, then the sweep** — the ~1 247 non-ASCII-path matroska files are identified

## Amendment (2026-10-13) — the codeset is read on a throwaway locale, never on the process's own (DEB-856)

Written while implementing FR-318-2. The requirement names the read as `nl_langinfo(CODESET)` *after the usual
`setlocale(LC_ALL, "")`*, and the **question** is exactly right — it is the effective charset that matters, not
the variable chain that produced it. The **mechanism** is not, and this records the substitution, because the
reason for it is the argument FR-318-2 already makes two bullets further down.

`setlocale(LC_ALL, "")` answers the question by **mutating this process's global locale for the rest of its
life**. That reaches every locale-sensitive libc call the backend makes — numeric formatting first among them,
where a locale with `,` for a decimal separator is the difference between a valid JSON body and an invalid one.
And it buys nothing: the fault this phase exists to surface is in **child** processes, and a child inherits the
*environment*, never our `setlocale` state. MKVToolNix calls `setlocale(LC_ALL, "")` for itself, out of the same
environment, whatever this process did to its own.

So the read is done on a locale object that is built, asked and thrown away:

```
newlocale(LC_ALL_MASK, "", null)  →  nl_langinfo_l(CODESET, it)  →  freelocale(it)
```

Same precedence chain (`LC_ALL` → `LC_CTYPE` → `LANG`), same answer, no global state touched. Measured with the
three calls in C, each run from an environment stripped of `LANG`, `LC_ALL` and `LC_CTYPE`:

| environment | `nl_langinfo_l(CODESET, …)` | the process's own `LC_CTYPE` after the read |
|---|---|---|
| `LC_ALL=C` | `ANSI_X3.4-1968` | `C` |
| `LC_ALL=C.UTF-8` | `UTF-8` | `C` |
| `LANG=C.UTF-8` | `UTF-8` | `C` |
| `LANG=xx_YY.UTF-8` (no such locale) | **`newlocale` → `NULL`** | `C` |

The first two strings are the ones the reproduction table reports, so the mechanism answers the same question
it does — and the right-hand column is the point: the process's locale is still `C` *after* the read, which a
`setlocale(LC_ALL, "")` could not say. This is the letter of FR-318-2 bending to its own last bullet: *the check reports;
it does not repair.* Adopting the environment is a far smaller repair than forcing UTF-8, but it is still the
process reaching into its own environment, and there is no reason to reach.

**One answer FR-318-2 had no case for**, surfaced only by writing the call: `newlocale` returns `NULL` when the
environment *names* a locale the system cannot provide — `LANG=fo_FO.UTF-8` in an image that carries only `C`
and `C.utf8` is the realistic way to get there, and `setlocale` would fail the same way and leave the C locale
standing. That reaches the pure function as the **empty string** the Tests section already demands a case for,
and it settles what that case must say: the sentence names *no* encoding and reads that the encoding could not
be determined. It is red either way — a process whose locale request failed cannot open a non-ASCII path, and
a check that cannot tell you the encoding is not a check that may pass.

Nothing else in FR-318-2 moves: one `WARN` on the `integrity` channel at startup, one health check beside
`mkvpropedit`'s and in its shape, no config key, no repair. The health check's `detail` and the `WARN` line are
built from **one consequence sentence in one place**, so the two surfaces cannot drift apart — the same
reasoning as FR-244-8's advisor/health pairing.

**Built and measured from the shipped Kotlin, not only from C** (`6fd6f39e`). The linked `linuxX64Test` binary
run by hand under three stripped environments — which is how to see what this read answers before the container
exists, and it needs no container, no deploy and no library:

| environment | `CharacterEncoding.effectiveCodeset()` | verdict | test result |
|---|---|---|---|
| `LC_ALL=C` | `ANSI_X3.4-1968` | **red** | 5 passed |
| `LC_ALL=C.UTF-8` | `UTF-8` | green | 5 passed |
| `LANG=xx_YY.UTF-8` (no such locale) | `''` (`newlocale` → `NULL`) | **red** | 5 passed |

The three rows are the Tests section's three cases reached through the real read rather than a literal, and the
middle one is what acceptance 4 will see once the container is recreated. **Acceptance 4 is therefore down to
the container alone** — the logic beneath it is proven here.

### FR-318-1's "a recreate picks it up with no rebuild" is false for prod as it stands

The requirement says the compose line *"lets the fix reach a running deployment by recreating the container
from the image it already has."* True in general. **Not true of prod**, because prod is not created from this
repository's `docker-compose.yml`. Raised by Viti on DEB-855 and verified here independently off the live
container's own compose labels:

```
com.docker.compose.project.config_files =
  /home/jeggy/jellystructure/dev-docker-compose.yml,
  /home/jeggy/jellystructure/deb754-clean-src.yml,
  /home/jeggy/jellystructure/deb754-avsync.yml
working_dir = /home/jeggy/jellystructure      service = backend
```

None of those three files is this repository's, **and none of them carries `LANG` or any `LC_*`**. Nor does the
running container's `Config.Env`, nor the image it runs (`jellystructure-backend:latest`, built before
`3f5fea79`). `/proc/1/environ` holds `PATH` plus exactly the variables that compose file sets — which is also
the proof that the `environment:` block is the lever. **So a bare `up -d --no-build` today is a no-op for this
bug**, and the repo's committed compose line reaches the dev and test stacks only.

Two routes exist, and **both are the owner's**, because one touches a file outside this repository and the
other rebuilds a live service:

1. **No rebuild, seconds.** One line — `LANG: C.UTF-8` — into the `backend.environment` block of

   beside `CORS_ALLOWED_ORIGINS`; then `up -d --no-build backend`. **That file is outside this repository, so
   no agent may edit it without being told to.**
2. **Rebuild.** Build the backend image from `3f5fea79` with the three `-f` files and `up -d backend` — the
   durable half, at the cost of a full Kotlin/Native release build.

**Decision (PO): 1 now, 2 at the next natural rebuild**, and the owner is asked for 1. Route 1 restores the
admin's track writes across ~30 % of the library in seconds; route 2 stops the fix depending on a compose file
remembering. Either way it recreates **`backend` only** — `avsync` stays up, pinned at `:deb319` with no
`build:` stanza, and rebuilding it is ~10 GB for nothing.

**FR-318-1 is not rewritten**: the `Dockerfile` line is still the durable half and the repo compose line is
still right for every stack built from this repository. What is corrected is the claim that it reaches *this*
deployment.

### "Measured" was undefined, and that is why two seats got 27 and 45

FR-317-23 defines the probe-failed marker as `mkv_audio_ids IS NULL` **"for a matroska row that has been
measured"** — and never says which rows those are. Two readings of the same table, minutes apart, gave
different counts:

| definition of *measured* | ASCII NULL | non-ASCII NULL | recovery set |
|---|---|---|---|
| `reason IS NULL` only (a clean measurement) | 27 | 96 | **123** |

**The second is correct, and the spec now says so.** The probe is attempted on the same write path for every

is why the measured population is a small fraction of the library and the eventual recovery set is nothing
like the 1 247 non-ASCII paths the phase opened with).

**Every count in this phase and in DEB-857's acceptance 6 uses the second definition:**
`reason IS NULL OR reason = 'no_faces'`. At 01:42:43Z that is **165 rows**, still climbing. The figure of 135
in §What is wrong is the 2026-10-12 reading and is left as the historical record.
